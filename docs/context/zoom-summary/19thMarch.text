RL Training Performance Optimization
Pulak identified performance issues with their RL training setup, where they were only achieving 450 steps per second with less than 10% GPU utilization despite the environment step time being 0.1 milliseconds. He implemented two optimizations: vectorizing environments to run multiple environments on the GPU simultaneously, and batching computations in memory to reduce data reloading. These changes resulted in a 26% improvement from single environment to 32 environments, followed by an additional 16% improvement, bringing the total speedup to around 40-45% and increasing steps per second from 450 to approximately 1200.
Batch Rollout Process Discussion
Pulak explained the batch rollout process, clarifying that different parts of the trace are used temporally across time steps, and updates to value and reward functions are cumulative and computed at the end of each batch. Yuhong inquired about the reward computation method, and Pulak confirmed that the reward for each rollout is based on the peak MPD usage within that rollout, not individual time steps. Pulak also discussed considering a rewrite in JAX but decided against it due to sufficient current performance and identified inter-trace IPC as a potential bottleneck.
RL System Performance Optimization
Pulak discussed optimizing his RL system’s performance by implementing lazy loading, which reduced trace loading time from 6 minutes to a lower but significant amount. He noted that while the current setup doesn’t fully utilize GPU resources due to alternating CPU and GPU operations during rollouts, he decided against over-optimizing by moving everything to GPU at this stage. Pulak mentioned he was conducting experiments with data augmentation and planned to share more details about his findings, including specific trace results.
VM Memory Data Analysis Discussion
Pulak and Yuhong discussed analyzing VM memory data and trace recordings. Yuhong explained that large VM memory allocations in the data were due to Azure bare metal servers, which allocate a single large VM per server. They examined a hotfix Yuhong had implemented to filter out VMs where memory usage exceeded MPD capacity, finding that scaling up the threshold would remove 60% of VMs due to trace recording noise. Pulak also identified an issue with termination dates being set to January 1st when not provided, which was causing incorrect data spikes. They discussed the potential for data augmentation by scaling up or down while preserving temporal patterns, focusing on VM count, memory allocation, and trace lifetimes.
